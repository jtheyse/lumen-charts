### The classic finish is 0.23.0

0.24.0 changes how every chart looks by default, so the release could not prove itself by leaving the baseline alone. It proves it the other way round: `ChartFinish.Classic` must reproduce 0.23.0 byte for byte, and every rendering may change only in the refined finish. The baseline harness hashes 189 renderings: every kind in both themes with and without titles, annotations, a density scatter, a brand, both graph layouts in both themes, and the guards each release since 0.19.0 added, through 0.23.0's gradients, fades, capsules, value labels, Midnight and panes. A classic mode was added to the harness first. It sets the finish on the style each chart draws with, its own or its theme's preset, and finds the property by name, so on code that has none it draws every spec as given. Run on 0.23.0's code it wrote the 189 hashes of the plain run, which is what made it a fair test; run on 0.24.0's it writes them again, all 189, gradient IDs included. The executable suite pins the classic finish to 0.23.0 too, through 29 of those hashes, among them a gradient on a chart with no style, one on a preset adjusted in C# and one on Midnight, and through every check written against 0.23.0's look, which now draws in the classic finish.

Gradient IDs needed care for that. They are named after a hash of the spec, and a chart moved to the classic finish carries a style it did not have before. A classic style is therefore serialized for hashing as 0.23.0 serialized it, without its finish, and a classic style that is its theme's own preset hashes as no style at all, so a chart on a theme moved to the classic finish names its gradients exactly as before. A refined chart hashes with the style it draws with, finish included, so a page showing one chart in both finishes never gives the two one ID; the contact sheet does just that. The one chart this cannot serve is one that set `Style = ChartStyle.Light` or `ChartStyle.Dark` explicitly in 0.23.0, which now takes its theme's IDs: the IDs change and nothing they paint does.

Every one of the 189 changes in the refined finish. A contact sheet of all of them, the classic rendering beside the refined one, was looked through for clipped text, labels over marks, missing marks, broken panes and wrong colours; what it found is listed under [Issues found and corrected](#issues-found-and-corrected).

Of the 106 hashed renderings exactly one changed, the guard with Y annotations on a horizontal bar chart, as intended; a new guard for zone bands on a horizontal bar chart, hashed before the change, matches, as does every other rendering. `AnnotationAxis` now documents that Y is the value axis wherever the chart draws it, and an X annotation stays refused on every category chart, horizontal bars included, because their bars stand at indices rather than at values.

- The gallery's dark theme failed axe-core's contrast rule on 13 nodes, all in the gallery's own chrome: the accent links, the intro caption, the selected chart, brand, axis and layout buttons, and the section labels. The accent `#4B66CA` and the section-label grey `#636D80` were fixed colours rather than theme tokens, so the dark theme kept the light theme's values: `#4B66CA` measured 3.46:1 on the dark page, 3.21:1 on its cards and sidebar and 2.69:1 on the accent card, and `#636D80` 3.44, 3.19 and 2.67. The browser suite swept the light theme only, so it never reached them. They are now the tokens `--accent` and `--eyebrow`, unchanged in the light theme and lightened in their own hue for the dark one to `#8295DA` (6.19, 5.76 and 4.82:1) and `#9099A9` (6.24, 5.80 and 4.85:1); every text use of the accent takes the token, so the headline and brand mark, which passed as large text, lighten with the rest. The suite now presses the gallery's theme button, waits for the chart to redraw in the dark colours so that it cannot sweep the light page by mistake, and sweeps again: 13 nodes failed before the change and none after it. The WebAssembly page has no theme button, so the sweep skips there with a SKIP line, and its only use of `#4B66CA`, a pressed button's text on white, measures 5.18:1, so nothing there needed changing.

- A zone scale checks its rules as it is constructed, which suits code but not a request: posted to the HTTP API, a scale whose bounds did not rise threw an `ArgumentException` from inside the JSON reader, before the endpoint's own handling, and was answered with a server error (500). The scale now reads through a converter that reports a broken scale as invalid JSON, which ASP.NET Core answers with 400 as it does any malformed body. A unit test and an HTTP check hold it there.

- Building duration axes found a hang that predates them. With minor gridlines on an axis whose values sit near 1e21, a tick step can be less than half the gap between neighbouring doubles, so adding it leaves the value where it was and the loop that places the minor lines never reaches the axis maximum. A plain numeric axis does it too — a replay of the old loop spun a million times without advancing — and the HTTP API accepted such a request. The loop now also counts its intervals, which never binds at ordinary magnitudes: the 73 renderings and seven guards, three of them with minor gridlines, match. A test runs the case under a time limit, and duration ticks are counted in whole steps for the same reason.

- The first drawing of a two-series histogram in the gallery misled the eye. With only the one-pixel gap between bins, a bin whose first series counted zero put its second bar flush against the next bin's first, so bars read as pairs across a bin edge. Several series now inset their group by a tenth of the bin on each side, which a test checks; a single series is untouched, which the hashed renderings confirm.

- The violin tests were written before the drawing was looked at, and two of them were wrong rather than the code: a distribution whose smallest and largest observations are themselves modes puts two of its three bulges at the ends of the grid, where a test looking for interior peaks finds nothing, and rounded coordinates make each peak two samples wide. Both expectations were corrected; the density estimate itself was right, and is checked against a trapezoidal area, a known peak location and a bimodal set whose valley is a quarter of its modes.

- A trend line fitted in raw data space jumped vertically at every weekend a trading axis left out, because the two edges of a skipped span share one position. A test that counted the segments in the drawn path caught it. Fitting in the space the chart draws in removes the jump and, on plain axes, changes nothing: least squares is unaffected by the scaling between data and pixels, which the 63 hashed renderings and the fit tests both confirm.

- A compressed time axis draws both edges of a skipped span at one position, which two tests caught as soon as they asked for a round trip. Reading that position back now gives the moment the axis resumes at, because that is where the data sits, and a tick where a span opens is dropped so that two labels cannot land on one pixel. The HTTP script found the second half of this: a holiday still printed its own date until the tick filter included the opening edge.

- Minor gridlines first changed all 63 hashed renderings even though no chart had asked for them, because their rule was added to the stylesheet every chart emits. The drawings were identical, but the property worth keeping is that nothing moves at all, so the rule is now emitted only by a chart that draws them, and the 63 renderings match again.

- Time zones were checked against the cases that break naive implementations before the feature was wired to a chart: day ticks in New York land on local midnight at 05:00 UTC, the ticks after the March clock change land at 04:00 UTC while still reading local midnight, and Kolkata's half-hour offset puts local hours at UTC half past. A chart without a zone is unchanged, which 63 hashed renderings confirm.

- The second Y axis was built so that a chart without one renders exactly as before: 63 renderings covering every kind in both themes, annotations, a density scatter, a branded chart and both graph layouts were hashed before the change and after it, and all 63 matched.

- Adding annotations broke two browser checks, for two different reasons. A dashed reference line was hoverable only where a dash happened to fall, because a pointer aimed at the line's centre landed in a gap; every line annotation now carries an invisible wider line that receives the pointer along its whole length. The checks themselves also assumed the first mark in a chart is a data mark, which annotations, histogram bins and box glyphs are not, so they now target `.lumen-datum[data-point]` explicitly.

- Branding was built so that a spec without a style must render exactly as before. Sixty-one renderings — every chart kind in both themes with and without native titles, a density scatter, and both graph layouts — were hashed before the change and again after it, and all sixty-one matched. The heatmap ramp, previously a hard-coded formula, is now an interpolation between two style colours that reproduces the old values exactly.
- The first browser check of `LumenBrand` reported the gallery's host font as `Segoe UI,Arial,sans-serif`, which is also the library's default, so a working resolver and a silent fallback would have looked identical. The WebAssembly sample was given its own typeface (`Trebuchet MS`) and brand so the browser suite can tell them apart; it confirms the resolved font and colour reach both the chart and its exported file, and it normalizes the page's colour with a canvas rather than the library's own resolver so a resolver bug cannot hide in the check.

- The first axe-core sweep reported colour-contrast failures on both sample hosts: 62 serious nodes in the gallery and 4 on the WebAssembly page. Every one came from sample styling, not from the library, whose own palette was already measured against both chart backgrounds. The gallery's muted text measured 3.73:1 on the page background, its section labels 3.23:1 on the accent card, its accent links 3.90:1, and its intro caption 2.72:1 because a container opacity composited the token into a lighter grey. The tokens were darkened to `#626D80`, `#636D80` and `#4B66CA`, and the opacity moved from the container onto the drawing it was meant to soften. On the WebAssembly page an unscoped `button` rule was colouring the component's own legend buttons; it is now scoped to that page's controls.

- The first browser-automated run failed on hover with `<svg> intercepts pointer events`. Marks on the first and last value sat exactly on the plot's clipping boundary, so half of each mark was clipped away and a pointer at its own centre landed on the boundary and missed. The clipping viewport is now inset by one marker radius, which also caps how far an out-of-range value can bleed when zoomed. Two of that run's three failures were faults in the new tests rather than the product: a drag aimed at a node group's centre, which falls in the gap between the circle and its label, and a mouse drag at viewport coordinates without scrolling the target into view first.

- The 0.6.0 contrast measurement failed three palette colors against the light background: `#18A999` at 2.93, `#DA9650` at 2.48 and `#58A4C1` at 2.80, all below the 3:1 needed for non-text contrast. - A Blazor WebAssembly host failed to build with `NETSDK1082`, hunting for an ASP.NET Core runtime pack for `browser-wasm`. A stock `dotnet new blazorwasm` project built cleanly on the same machine, which located the cause in this repository: `Lumen.Charts.Blazor` declared `<FrameworkReference Include="Microsoft.AspNetCore.App"/>`, requiring the ASP.NET Core shared framework that a WebAssembly host does not have. The component library was therefore unusable in WebAssembly, not merely untested. ## Practical limits

Browser timings now have their own record in [PERFORMANCE.md](PERFORMANCE.md), measured with `tests/Lumen.Charts.Profile` against headless Chromium. The profiler is deliberately outside continuous integration: a timing gate on a shared runner fails for reasons unrelated to the code.


A diagnostic run generated an SVG from 100,000 line observations in approximately 60 ms with at most 1,200 rendered sample points on this machine. This measures SVG generation only, not network time, browser layout, interaction latency or memory, and is not a comparison with another library.

WebAssembly hosting is exercised by the sample above but not under production load or on other browsers. Screen-reader conformance, production load, all operating systems, touch interaction, and very dense graphs have not been certified. Very large scatter/bubble inputs render every point. Dense graph layouts and extreme chart proportions still need application-level review. See README and RESEARCH.md for the exact scope and future capabilities.
